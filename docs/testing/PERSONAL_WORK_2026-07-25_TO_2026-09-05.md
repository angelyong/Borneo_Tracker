## 5. Problems Encountered and How I Resolved Them

| Problem Encountered | Effect on the Project | Resolution | Result |
|---|---|---|---|
| AI-generated simulation answers could introduce numbers that were not calculated by the project. | Users could receive unsupported or misleading resilience claims. | Kept the calculation deterministic and added an approved-number validator plus safe fallback behavior. | The AI explains calculated results but is not allowed to invent new values. |
| A scenario calculation could use incompatible units or missing pillar inputs. | An invalid calculation could create a misleading complete score. | Added model contracts, unit checks and missing-data behavior that leaves unsupported pillars unscored. | Missing or incompatible data is shown honestly. |
| Dashboard search produced no useful next action when a location was not found. | The user reached a dead end. | Added an “Ask BorneoBot” option that opens the chat with the original question prefilled. | Users can continue their investigation without retyping the question. |
| AI requests could reach a quota limit and return HTTP 429. | The chat experience could fail without useful guidance. | Added localized quota handling and a safe non-fabricated fallback. | Users receive a controlled capacity message or safe guidance. |
| HexRadar was primarily visual and did not provide direct access to the supporting indicators. | Keyboard users and users needing evidence could not inspect a pillar easily. | Added click, Enter and Space interaction and a pillar drill-down panel. | Pillar information became accessible and evidence-oriented. |
| The initial translation test compared every English and Malay leaf key directly. | Valid Malay translations were incorrectly reported as missing because Malay does not require English `_one` variants. | Normalized recognized plural suffixes and compared translation roots. | UT-012 passed without adding unnecessary Malay singular keys. |
| Integration tests derived project paths from module URLs on Windows. | The path format caused incorrect project-root matching. | Resolved test paths from `process.cwd()` with the platform path utility. | The deployment-package integration test passed on Windows. |
| A Playwright assertion targeted both `main` and `body`. | More than one matching element could make the assertion unstable. | Changed the assertion to use the page body as a single stable target. | Direct-route checks ran without the locator conflict. |
| Attachment tests expected only one exact error sentence. | Correct application behavior could fail because equivalent wording was used. | Allowed the known valid invalid-type and size-limit messages while preserving the behavioral assertion. | Invalid and oversized attachment cases passed correctly. |
| Twenty-one Playwright cases required staging accounts, credentials, email links or admin/news fixtures and were skipped in the local automated run. | The automated report showed 21 skipped cases even though the scenarios were still required. | Documented the staging requirements and manually executed the remaining scenarios. | All 21 were manually confirmed as passed; the final catalogue records 70 passed cases. |
| BT-19 and BT-20 initially depended on resilience-history and source-registry data that was not available on my Wave 3 front-end branch. | Implementing those interfaces immediately would have required fake data or duplicated backend logic. | Documented the dependency and left the features blocked until the required data contracts were supplied. | The project preserved honest data handling, and the features were later completed through the team workflow. |
